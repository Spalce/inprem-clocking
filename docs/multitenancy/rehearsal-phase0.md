# Phase 0 migration rehearsal

Phase 0 step 0.10; design section 11. This records how the Phase 0 schema change was rehearsed, the timings, and what must still happen before the change goes near a shared or production database.

## What is applied

The Phase 0 schema change is applied as one guarded bundle, `scripts/migrations/phase0-up.sql`, with `phase0-down.sql` to reverse it. Both are generated by `scripts/migrations/build-phase0-bundle.ps1` from the reviewed per-migration scripts. CI fails if the committed bundles differ from what the builder produces.

| Order | Script | Design migration | What it does |
|---|---|---|---|
| 1 | `platform-M1a` | M1, platform tables | Schema `platform`; data-protection keys |
| 2 | `platform-M2` | M2, memberships | `TenantMemberships`, filled from `AspNetUsers.TenantId` |
| 3 | `app-M3` | M3, unique email | Platform-wide unique email (guard 50003) |
| 4 | `app-M4` | M4, composite keys | Sessions can only point at a person of their own organization (guard 50004) |
| 5 | `platform-M1b` | M1, platform tables | Provider users, provider invitations, recovery records, audit (append-only), used codes, attempts |
| 6 | `hangfire` | (D6) | Job storage, schema `hangfire` |

**M1, the "platform tables shell":** step 0.10 asks for empty `ProviderUsers`, `Invitations`, `AuditEntries` and `RecoveryRecords`. They already exist:
- M1a and M1b together are design migration M1 for Phase 0;
- M1b was created in step 0.7, because bootstrap and recovery need those tables;
- the invitations table is named `ProviderInvitations`, to keep it apart from organization invitations (memberships).

No second, duplicate migration was added. The remaining M1 tables (plans, prices, payments and so on) come with the phases that use them.

**Guards added to the bundles (design 11.3):**
- SQLCMD mode is required (otherwise nothing runs), and the bundle stops at the first error.
- It refuses a database that isn't at the approved app's last migration (`20261003091001_AddVolunteerContactPersonDetails`) with "wrong database?". It also refuses one that has app or platform migrations the bundle doesn't know.
- At the end, it refuses to report success unless every migration is recorded (up) or none is left (down).

## How to repeat it

```powershell
dotnet build InpremClockingApp/InpremClockingApp.csproj -c Release
pwsh scripts/rehearsal/rehearse-phase0.ps1 -AppDll InpremClockingApp/bin/Release/net8.0/InpremClockingApp.dll
```

Without options, the driver does this on LocalDB:
1. Creates a disposable database at the approved app's last migration.
2. Fills it with synthetic data (`scripts/rehearsal/seed-rehearsal-data.sql`).
3. Runs every step below, timing each one.
4. Compares the approved app's data with a fingerprint taken first (`scripts/rehearsal/fingerprint.sql`: row counts, hour totals per organization, checksums).
5. Drops the database.

For a **restored copy of the real database**:
- restore it under a name containing `Rehearsal`;
- add `-Existing`, which skips creating and seeding;
- add `-Keep` if the restored copy should not be dropped at the end.

## Rehearsal of 2026-10-13

**Environment:** LocalDB (SQL Server 2022 Express LocalDB) on the developer machine, with a Release build of `mt/phase0` at step 0.10.

**Data:**
- 3 organizations (the house one plus two);
- 4 admins, one organization having two;
- 300 people;
- 120,000 completed sessions (400 days);
- backup size 24 MB.

| Step | Seconds | Result |
|---|---:|---|

| Seed synthetic data | 4.9 | 3 orgs, 4 admins, 300 people, 120,000 sessions |
| 1 Inspect (data quality, fingerprint) | 2.2 | `04-data-quality.sql` ran; fingerprint has 27 rows |

**M2 `1/4/0/1`:** one organization has no Owner yet, because it has two admins. That is the expected M2 case: verify lists it so someone can name the Owner.

**Timing and window (design 11.3):**
- Apply takes about 2 seconds, and rollback by script about 1 second.
- Restoring a 24 MB backup takes about 3 seconds.
- A **30-minute change window** leaves well over 50% spare, even if the real database is many times larger. Confirm on the restored copy.

**The rehearsal found and fixed two problems:**
1. **The bundle's guard failed on a database without the platform schema.** SQL Server resolves table names when it compiles a batch, so naming `platform.__EFMigrationsHistory` stopped the batch before the `IF` that checks for it. On an empty database the same happened with `dbo.__EFMigrationsHistory`, which stopped safely but with an unclear message. Those checks now run as dynamic SQL, or in their own batch.
2. **The synthetic data had no roles,** so starting the app created them and the fingerprint changed. That is normal app behaviour; real databases always have the roles. The seed now creates them as the app does.

## Still to do before a shared or production database (design 11.1–11.4)

- **Restored copy:** rehearse on a restored copy of the database that will actually be changed, using `-Existing`, and record it below.
  - The test-deployment backup from G0 is not used, because the new app won't go live on that data.
  - If the new app takes over the old app's real database, inspect it first (`scripts/inspection`, design 11.1).
- **Backup proof:** prove that backup's restore, with the row counts and three report totals agreed with the project owner (design 11.2).
- **Sign-off:** the CTO signs the scripts, the inspection results, these timings, and the go/no-go criteria (design 11.4).
