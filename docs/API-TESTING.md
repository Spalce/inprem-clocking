# Inprem Clock-in Website API Testing Guide

## Test environment

Current deployed base URL:

```text
https://inprem-003-site3.etempurl.com/api/public/v1
```

Before testing tenant registration, confirm the deployment is running the current API version.

## 1. Test the health endpoint

This endpoint can be opened directly in a browser:

```text
https://inprem-003-site3.etempurl.com/api/public/v1/health
```

Expected result:

```json
{
  "status": "ok"
}
```

This confirms that the API is reachable. It does not by itself prove that signup, email, CAPTCHA, database, or checkout configuration is working.

## How to get the CAPTCHA token

The CAPTCHA token is generated by Cloudflare Turnstile in the website form. It is not a permanent value and should not be invented or copied from an old request.

### Recommended method: use the demo registration page

1. Open the deployed demo website, if it is enabled:

   ```text
   https://inprem-003-site3.etempurl.com/demo-site/
   ```

2. Open the signup/registration page.
3. Complete the form.
4. Wait for the CAPTCHA widget to complete.
5. Submit the form through the demo website.

The demo website automatically reads the current CAPTCHA token and sends it as `captchaToken` to `POST /signups`. You normally do not need to see or copy the token.

### If using Postman

Postman does not generate a Turnstile token. Use the demo website or the real frontend to obtain a current token, then use it immediately in the Postman request. CAPTCHA tokens are short-lived and may be rejected if reused.

If the demo website is not available, ask the deployment owner to provide a QA CAPTCHA setup or a documented test-token configuration. Do not use production CAPTCHA secrets in Postman.

### Local test configuration

For local development only, the demo-site README describes Cloudflare test keys and an optional configured test token. A test token works only when the server has been explicitly configured to accept that value. It is not automatically valid on the deployed environment.

If the API returns `captcha_failed`, the request reached the API but the CAPTCHA token was missing, expired, or not valid for that environment.

## 2. Test the read-only public endpoints

The following requests can be opened in a browser or sent from Postman:

```text
GET https://inprem-003-site3.etempurl.com/api/public/v1/plans
GET https://inprem-003-site3.etempurl.com/api/public/v1/timezones
GET https://inprem-003-site3.etempurl.com/api/public/v1/slugs/test-center/availability
```

Expected checks:

- `/plans` returns at least one active public plan and price for signup testing.
- `/timezones` returns a JSON array.
- `/slugs/test-center/availability` returns the normalized slug, availability, and any suggestion.

The API root itself is not a test endpoint:

```text
https://inprem-003-site3.etempurl.com/api/public/v1
```

A not-found response there is expected because no root `GET` route is defined.

## 3. Test tenant registration with Postman

Create a `POST` request:

```text
https://inprem-003-site3.etempurl.com/api/public/v1/signups
```

Headers:

```text
Content-Type: application/json
Idempotency-Key: {{unique-idempotency-key}}
```

Use a new test email and a unique slug for each successful registration. Get `planPriceId` from `/plans`.

Request body:

```json
{
  "organizationName": "API Test Organization",
  "slug": "api-test-organization-001",
  "timeZone": "America/New_York",
  "owner": {
	"firstName": "API",
	"lastName": "Tester",
	"email": "api-tester@example.com",
	"mobile": "+15551234567"
  },
  "consent": {
	"acceptTerms": true,
	"acceptPrivacyPolicy": true,
	"smsOptIn": false
  },
  "planPriceId": "PLAN-PRICE-ID-FROM-PLANS",
  "mode": "trial",
  "captchaToken": "TOKEN-FROM-CAPTCHA-WIDGET"
}
```

Expected successful response:

- HTTP status: `201 Created`
- `status`: `PendingVerification`
- `nextAction`: `verify_email`
- A `signupId`
- A temporary `signupToken`
- A `signupTokenExpiresAt` value

A browser test of `/signups` is not valid because the browser sends `GET`, while registration requires `POST` with JSON, headers, and CAPTCHA.

## 4. Test tenant registration with PowerShell

Run this from PowerShell after obtaining a real `planPriceId` and a valid CAPTCHA token:

```powershell
$baseUrl = "https://inprem-003-site3.etempurl.com/api/public/v1"
$body = @{
	organizationName = "API Test Organization"
	slug = "api-test-organization-001"
	timeZone = "America/New_York"
	owner = @{
		firstName = "API"
		lastName = "Tester"
		email = "api-tester@example.com"
		mobile = "+15551234567"
	}
	consent = @{
		acceptTerms = $true
		acceptPrivacyPolicy = $true
		smsOptIn = $false
	}
	planPriceId = "PLAN-PRICE-ID-FROM-PLANS"
	mode = "trial"
	captchaToken = "TOKEN-FROM-CAPTCHA-WIDGET"
} | ConvertTo-Json -Depth 5

$response = Invoke-WebRequest `
	-Method Post `
	-Uri "$baseUrl/signups" `
	-Headers @{ "Idempotency-Key" = [guid]::NewGuid().ToString() } `
	-ContentType "application/json" `
	-Body $body

$response.StatusCode
$response.Content
```

Do not commit real signup tokens, CAPTCHA tokens, email credentials, or production data to source control.

## 5. Test signup status

Copy `signupId` and `signupToken` from the successful signup response.

```text
GET https://inprem-003-site3.etempurl.com/api/public/v1/signups/{signupId}
```

Header:

```text
Authorization: Bearer {signupToken}
```

Expected initial response:

```json
{
  "signupId": "SIGNUP-ID",
  "status": "PendingVerification",
  "subscriptionStatus": "Trialing"
}
```

The exact subscription status depends on the selected plan and mode.

## 6. Test the verification email

Use the test owner's email address and verify that:

1. An email is delivered.
2. The link opens `/Account/VerifyEmail` on the deployed application.
3. The owner can enter and confirm a password.
4. Weak passwords are rejected.
5. Mismatched passwords are rejected.
6. A valid verification changes the signup and organization to the verified/active state.
7. The owner can sign in after verification.
8. The verification link cannot be reused successfully.

If email is not configured in the test environment, use the configured email test sink or mail-capture service. Do not use a real customer mailbox for automated tests.

## 7. Test resend verification

```text
POST https://inprem-003-site3.etempurl.com/api/public/v1/signups/{signupId}/resend-verification
```

Header:

```text
Authorization: Bearer {signupToken}
```

Expected results:

- `202 Accepted` when another message is sent.
- `409` with `already_verified` after verification.
- `409` with `resend_limit_reached` after the hourly limit is exceeded.

## 8. Test idempotency

Send the same `POST /signups` request twice with the same `Idempotency-Key` and the same body.

Expected result:

- The second request returns the stored first response rather than creating another tenant.

Then reuse the same idempotency key with a different body.

Expected result:

- The request is rejected with the idempotency-key conflict response.

Use a fresh unique idempotency key for each new registration attempt.

## 9. Test validation and conflict responses

Test each of these separately:

| Test | Expected result |
|---|---|
| Missing JSON body | `400`, `validation_failed` |
| Missing organization name | `400`, `validation_failed` |
| Invalid slug | `400`, `validation_failed` |
| Existing slug | `409`, `slug_taken` |
| Invalid owner email | `400`, `validation_failed` |
| Existing owner email | `409`, `email_in_use` |
| Terms not accepted | `400`, `validation_failed` |
| Privacy policy not accepted | `400`, `validation_failed` |
| Invalid CAPTCHA | `400`, `captcha_failed` |
| Unknown or inactive plan price | `400`, `plan_not_available` |
| Invalid idempotency key | `400`, `validation_failed` or the documented idempotency error |
| Too many requests | `429`, `rate_limited`, with `Retry-After` |

Error responses use `application/problem+json`. Check the response `code`, `errors`, and `traceId` fields.

## 10. Test token security

Using a signup token, verify that:

- The token can read only its own signup.
- A missing token returns `401`.
- A malformed token returns `401`.
- An expired token returns `401`.
- A token for signup A cannot access signup B.
- A billing access token cannot be used as a signup token.
- The token is not printed in normal application error messages.

Tokens are temporary secrets. Delete them from Postman history and test logs after testing.

## 11. Test checkout for a paid plan

Create a checkout request using the signup token:

```text
POST https://inprem-003-site3.etempurl.com/api/public/v1/checkout-sessions
```

Headers:

```text
Authorization: Bearer {signupToken}
Content-Type: application/json
Idempotency-Key: {unique-idempotency-key}
```

Body:

```json
{
  "planPriceId": "PLAN-PRICE-ID",
  "purpose": "new",
  "returnUrl": "https://frontend.example.com/checkout/complete",
  "cancelUrl": "https://frontend.example.com/checkout/cancelled"
}
```

Expected successful response:

- HTTP status: `201 Created`
- A `checkoutSessionId`
- An `approvalUrl`
- An `expiresAt` value

Then test:

```text
GET  https://inprem-003-site3.etempurl.com/api/public/v1/checkout-sessions/{checkoutSessionId}
POST https://inprem-003-site3.etempurl.com/api/public/v1/checkout-sessions/{checkoutSessionId}/confirm
POST https://inprem-003-site3.etempurl.com/api/public/v1/checkout-sessions/{checkoutSessionId}/cancel
```

Use the same bearer token and follow the payment provider's sandbox process. Checkout tests require the payment provider to be configured and available.

## 12. Test CORS from the frontend origin

From the actual frontend website, test a request such as:

```javascript
fetch("https://inprem-003-site3.etempurl.com/api/public/v1/plans")
  .then(response => response.json())
  .then(data => console.log(data));
```

Confirm that the browser does not report a CORS error. The frontend origin must be present in the application's `Site:PublicWebsiteOrigins` configuration.

## 13. Minimum acceptance result

The API can be reported as successfully tested when:

- Health returns `200`.
- Plans and time zones return `200`.
- A valid signup returns `201`.
- Duplicate email and slug cases are rejected correctly.
- CAPTCHA is enforced.
- The verification email arrives and activates the owner account.
- Signup status works with the returned token.
- Cross-signup access is rejected.
- Idempotency prevents duplicate tenant creation.
- Rate limiting returns `429` when exceeded.
- The frontend origin can call the API without a CORS error.
- Checkout succeeds in the payment sandbox, if paid registration is required.
